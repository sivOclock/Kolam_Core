# Session 2026-10-13 — from Python generator to Rust generation + Python feed

Where things stood at the start: the Python package `kolam_press` generated kolams, rendered images
and wrote labels; the gap code had just become the training target. Where they stand at the end:
two parts, `kolam_gen/` (Rust) makes kolam encodings at scale, `kolam_feed/` (Python) reads,
renders, checks and — next — trains.

```text
kolam_gen (Rust)                              kolam_feed (Python)
4 systems → gaps + horns → checks → encoding  →  encoding → hypergraph → strokes → image → model
                                     shards       rendered on the fly, new look each epoch
```

## Decisions

| decision | why |
|---|---|
| The training label is called the **kolam encoding** (was "gap code"); not "embeddings" | "embedding" means a learned float vector in ML; this label is exact and discrete |
| Store **encodings only**; render images while training, never save training images | 1M kolams ≈ 290 MB of encodings vs 38–124 GB of images; fresh augmentation every epoch; nothing to delete |
| Generation in **Rust** (`kolam_gen/`), all four systems mixed | Python made ~15 kolams/s (1M ≈ 20 h); Rust makes 1,300–2,500/s |
| **`kolam_press` deleted**; reading, rendering, checking moved to **`kolam_feed/`** (Python) | two parts only; rendering and training stay in Python, so no Rust renderer or Python bindings |
| **Training happens in `kolam_feed/`** | user's choice; no separate training directory |
| Python stays an **independent checker** of Rust | 180 reference kolams frozen from the retired Python generator (`tests/fixtures/kolams.jsonl`); both must keep giving their answers |
| Duplicates (same encoding) are drawn again in the **same system**; after 50 tries the slot is **dropped**, never kept | first version re-picked the system on redraw and the mix drifted (switching 10% instead of 15%) |
| Max grid stays **32** (label rule); train mostly on small grids | at 448 px a 32×32 kolam has lines under 1 px and a ~2,200-token answer; big kolams are read by tiles (VLM) or crops (CNN) |

## What was built

- **Docs cleanup.** `examples/` had been deleted while WFC still read `examples/sikku_diamond.kolam`;
  the photographed sikku is now an encoding inside the Rust code (`WFC_SOURCE_ENCODING`, marked
  REQUIRED). Stale references removed.
- **Rename** gap code → kolam encoding everywhere (`encoding.py`, `to_encoding`/`from_encoding`, field
  `encoding`).
- **Studio encodings page** (`kolam_studio/encodings.html`): paste many encodings, one chalkboard each;
  TS reader `src/kolam/encoding.ts` (same programs as Python on 100 encodings).
- **`kolam_gen/`** (Rust, ~1,700 lines): brush spec from `brushes.json`, label rules, symmetry, the four
  systems (random, substitution, switching, WFC), gate compiler, `drawn()` (capsules, box holes, horn
  growth), geometry check with a spatial grid, encodings. Commands:
  `generate` (shards of 50k, resumable, parallel, deterministic from seed/index/attempt),
  `check` (geometry stats per encoding), `big` (one kolam of any size).
- **`kolam_feed/`** (Python): `KolamDataset` (renders on the fly, `set_epoch`, `transform`), `collate`,
  `verify` (streaming, independent re-check), `preview`, `bench`; plus the model code moved from
  `kolam_press` (spec, hypergraph, encoding incl. `allowed_next`, compiler, geometry, render).
- **Tests** (25): encoding round trips on the reference kolams, the notebook's `build_crossing_loop`
  (restored), Rust and Python geometry against the references, generated encodings pass the Python
  checks, resume, `big`, dataset rendering.

## How the grid size is chosen

Per kolam: pick the system by `--mix`; the system picks its grid — random: rows and cols uniform in
`--min-size..--max-size` (3–8), 50% square; substitution: 6, 8, 9 or 12; switching and WFC: 5–11,
square, with a square / diamond / octagon / plus layout. Then empty border rows/cols are cropped.
Most common in 100k: 8×8 14%, 9×9 10%, 6×6 9.7%, 7×7 9.5%, 5×5 7.8%.

## Open

- **Switching and substitution run out of new designs**: at 100k they already needed more than one redraw
  per kolam (17,410 and 12,416). A 1M run may drop slots; the manifest reports drops per system.
  Not yet measured at 1M.
- **Grid size control**: only the random system follows `--min-size/--max-size`; a size-weights option
  for all systems would let us set e.g. "mostly ≤ 8, some 9–16".
- **Augmentation to add** in `kolam_feed` (all label-preserving): small rotation / perspective, scale and
  shift, floor and paper textures, lighting, JPEG, uneven chalk lines. 90° turns and mirrors change the
  encoding, so they need the label transformed too.
- **Training in `kolam_feed`**: prompt format and loss masking, validation/test split taken from the same
  run (rendered once, kept), scoring (exact match, % gaps right, % valid), constrained decoding with
  `allowed_next`. Pick the first model (a VLM such as Qwen-VL — check its tokenizer splits digits — or a
  scratch transformer with the 11 tokens) and the GPU. PyTorch is not installed yet.
- Commit the deletion of `kolam_press` and the move to `kolam_feed` (last commit, `99110c1`, is before it).
